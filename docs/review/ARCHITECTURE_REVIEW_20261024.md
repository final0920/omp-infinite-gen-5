# 无限五代：能力与架构评估

2026-10-24。编制者：AI 代理。**数字来自实测脚本，判断是我的意见。** 没有读过全部 164 个模块，结论针对整体形态而不是逐行实现。

## 1. 先给结论

- **工程骨架是好的**：分层清楚、无循环依赖、宿主耦合面很小、失败默认关闭、证据纪律严格。
- **能力投入的方向有偏差**：大量精力在"证明自己没有夸大"，而不是"让分析者更快得到正确结果"；能力证据全部停在自造样本，**没有一项到达真实目标**。
- **最直接的架构问题是模型看到的工具面太重**：默认的 Core 8 就要占约 1.3 万 token，其中一个工具占了 81%。
- **"辅助模型是否有用"这个核心问题至今没有答案**，现有的对照实验题目太简单，无法区分。

## 3. 做得好的地方（应该保留）

1. **分层干净**：无循环依赖、无层间违规；平台底座只有 2,485 行。
2. **宿主耦合面小**：只有 7 个文件碰到 DSH。这意味着把核心能力包装成 MCP 服务或别的宿主，工作量是"写一个适配层"，而不是"重写"。
3. **失败默认关闭的文化**：租约按进程创建身份判断、部分提交保留凭据、预算可冻结。这些在政府场景很值钱。
4. **进程隔离**：每个会话一个 Python worker，JSONL 通信，超时和取消可控。
5. **测试意识**：有同预算对照实验的框架（F13：冻结预算、独立核算成本），问题是题目，不是方法。

## 4. 主要问题

### 4.1 工具面太重，而且 Core 不"core"（架构）
- `ig5_profile` 是个万能工具：引擎状态、项目、工作区（32 个 action）、VM 恢复规划、记忆、知识库、协作、历史归档、客体调试、工具集切换，全塞在一个工具里，且**默认暴露**。
- 代价有三层：每次对话先付约 1 万 token；模型在 12 个参数、32 个 action 里选错的概率上升（评审已记录过 `search` 与 `documents` 被混淆）；`ig5_profile` 的任何一个子功能出问题，都影响默认路径。
- 这与"Core 8 是日常入口"的设计意图矛盾。

### 4.2 能力证据全部是自造样本，没有一项到达真实目标（能力）
- `CAPABILITIES.md` 里最高等级是 L3（真实原生执行，仅自产样本）。**L4（真实目标/业务恢复）为空。**
- F13 对照实验：30 次，题目是"8 位加零表达式"和"HALT 小 VM"，基线就是满分，所以区分不出差别；E 组比 A 组成功数一样，多用 2.33 次调用、约 2,078 token、3.4 秒。**这个实验既不能证明有用，也不能证明没用。**
- 结论：现在无法回答"IG5 比裸 Ghidra 加一个通用 MCP 强在哪"。

### 4.3 垂直研究占比过高，且不泛化（投入方向）
- `vm_*` 簇、15 个按 handler/context 编号写的证明、CFF 覆盖层、位向量候选验证，都是对特定 VM/混淆家族的研究。它们换样本或重新编译就失效。
- 这类工作有研究价值，但它不应占用默认路径，也不应成为产品的主要叙事。政府/警务场景更常见的需求是：恶意样本分诊、字符串/配置解密、协议还原、固件与移动端分析。

### 4.4 商业 Reverse 分支维护成本高、价值低（工程）
- `worker/ig5_worker.py` 1,544 行，是只服务商业 IDA 的第二套实现。独立评审发现的 8 项里 4 项只出在这一分支；本机该 IDA 的 DLL 无法加载，所以这条分支**连实测都做不了**。
- 默认走的是内置 Ghidra。这条分支的存在让关键审查面多了 1,544 行，且每加一个能力要写两遍。

### 4.5 "记账"重于"产出"（比例）
- 回执、哈希、预算冻结、"不升级结论"的边界声明，构成了大量代码和文档。严谨本身是对的，但它们现在是主要产出，而分析者能直接受益的能力很少。

### 4.6 测试结构（工程）
- 75 个 Python 测试大多不在默认门禁里；77 个原生测试需要手动运行。这次评审发现的 R1–R5 正好藏在"Python 与原生"这一侧。

## 5. 建议（按优先级，附粗略工作量与验证方式）

| # | 建议 | 工作量 | 怎么验证 |
| :-: | :--- | :--- | :--- |
| 1 | **瘦身工具面**：把 `ig5_profile` 拆成若干小工具（`ig5_status`、`ig5_workspace`、`ig5_memory`、`ig5_knowledge`…），Core 里只保留状态类的轻量部分，其余按需加载。目标：Core ≤ 4k token | 2–4 天（要改入口、测试、文档，`scripts/test_public_tool_catalog` 的 40 个工具契约需要同步评审） | 用 `tool_surface.mjs` 量体积；用同一批任务比较选错率 |
| 2 | **建带标准答案的评测集并公开方法**：每题有可核对的答案（解出的字符串/密钥/协议字段/函数语义），分"裸 Ghidra"、"IG5 Core"、"IG5 Full"三组，同预算、盲测、足够难（基线不能满分） | 1–2 周（复用 F13 的冻结预算和独立核算框架，重点是题目与样本） | 看 E−A 是否显著；样本量按置信区间设 |
| 3 | **把验证做成主打：AI 提假设、机器验证**。优先做三件高频任务：①解密/去混淆字符串例程的自动仿真与批量解码（Unicorn 已在）；②加密例程识别后用已知向量验证；③结构体/函数语义用差分仿真交叉核对 | 每项 1–2 周 | 评测集里这三类题目的正确率与误报率 |
| 4 | **垂直研究下沉成可选扩展**：`vm_*`、CFF、位向量、15 个样本证明移出默认路径与默认发行包，不在对外材料里作为主能力 | 3–5 天（已有登记清单和分层，机械成分大；注意 `runtime_pack.ps1` 里硬编码了路径） | 打包检查、安装包体积、默认工具面 |
| 5 | **冻结商业 Reverse 分支**：不再加新能力，从关键审查面里划出，除非有明确客户在用。若无人使用就删除 | 1–2 天评估 + 视决定而定 | 确认没有用户依赖；审查面减少 1,544 行 |
| 6 | **提供 MCP 适配层**：核心与宿主耦合只有 7 个文件，可以做一个与 DSH 无关的入口，让别的智能体宿主也能用 | 1 周左右（含审批与审计语义的对齐——这是难点） | 在另一个宿主里跑通 Core 流程 |
| 7 | **把 Python 单测纳入默认门禁**，原生测试按需分层运行 | 2–3 天 | 门禁覆盖的 Python 文件比例 |

我的优先排序理由：1 和 2 成本低且互相支撑（先瘦身再度量）；3 是真正的能力提升；4 和 5 是在为 3 腾出资源和审查面；6、7 是长期。

## 7. 这份评估的边界
- 工具体积用估算 token，只能比较量级；真实占用以宿主的分词为准。
- 没有逐个运行 40 个工具，也没有评估各分析引擎的结果质量。
- "没有 L4 证据"指文档里没有；不排除私下做过但未记录。
- 所有判断需要你们团队里熟悉场景的人复核。
